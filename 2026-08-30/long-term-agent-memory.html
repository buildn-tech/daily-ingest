Daily Ingest — Long-Term Memory: Store Evidence, Not Just Context

Memory research is moving beyond “bigger context.” The practical question is what an agent should retain, when it should update, and how a human can inspect or correct the resulting state. That makes memory a product and governance surface, not a hidden prompt trick.

Titans + MIRAS

STRONGFIELD NOTE
  • source: research.google
  • lens: practical leverage · evidence before automation

What it is

Google Research presents a long-term memory architecture and framework using selective, surprise-driven updates during inference.

Why it matters

A useful memory system needs retention and forgetting policies, not indiscriminate transcript accumulation.

Buildn / client use

Separate Buildn memory into durable facts, working context, and evidence links; give each a retention rule.
Caveat: Research architecture is not a drop-in agent-memory product.

Next action

Implement a tiny surprise/novelty queue for one workflow and inspect what it chooses to retain.

Differentiated memory for scientific cognition

WATCHFIELD NOTE
  • source: www.frontiersin.org
  • lens: practical leverage · evidence before automation

What it is

A 2026 framework proposal arguing that research agents need differentiated memory types for scientific work.

Why it matters

Different tasks need different memory: observations, hypotheses, methods, provenance, and contradictions should not collapse into one vector store.

Buildn / client use

Use typed memory lanes in research dossiers and client knowledge systems.
Caveat: Framework proposals need empirical validation and careful schema design.

Next action

Define five memory types for one research workflow and require provenance on each.

Evidence-linked retrieval

STRONGFIELD NOTE
  • source: research.google
  • lens: practical leverage · evidence before automation

What it is

A practical design pattern: retrieve claims with source, timestamp, confidence, and update path rather than naked text snippets.

Why it matters

Memory without provenance becomes unreviewable folklore; evidence makes correction possible.

Buildn / client use

Make every persistent Buildn memory item carry a direct source link and last-verified date.
Caveat: Provenance itself can become stale and needs refresh policy.

Next action

Add `source_url`, `observed_at`, and `review_by` to the next memory record.

Forgetting as a product decision

WATCHFIELD NOTE
  • source: www.frontiersin.org
  • lens: practical leverage · evidence before automation

What it is

Selective forgetting treats outdated, low-value, or contradicted state as a first-class lifecycle event.

Why it matters

Unbounded memory increases latency, privacy exposure, and the chance of stale decisions.

Buildn / client use

Offer clients a memory retention policy with expiry, correction, and deletion controls.
Caveat: Automatic forgetting can remove useful context; preserve an audit trail where appropriate.

Next action

Run a 30-day review on one memory store and classify stale versus durable items.

Memory evaluation loop

WATCHFIELD NOTE
  • source: research.google
  • lens: practical leverage · evidence before automation

What it is

Evaluate memory by downstream task improvement and correction cost, not by recall alone.

Why it matters

The right metric is whether retained state improves accepted work without increasing errors or review burden.

Buildn / client use

Track memory hit rate, accepted-use rate, contradiction rate, and time-to-correct.
Caveat: Metrics need a task-specific baseline and can be gamed by over-retention.

Next action

Create a ten-task benchmark with and without memory, then inspect failure modes.
