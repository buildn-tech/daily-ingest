Agent Runtime Efficiency + Context Hygiene

Long-horizon agents fail at the seams: compaction, saliency, and harness overhead. The practical move is to treat context as a budgeted, observable resource—not an invisible model detail.

Editorial readout

The ledger has covered memory content; this lane explores the neglected runtime question: when to compact, what to preserve, and how harness complexity changes cost and reliability.

Signal map

Green = actionable signal · amber = caveat or emerging risk · grey = connective tissue.

Transparent Context Compaction

PRACTICALPAPER
  • Source: arXiv 2610.20116
  • Signal: retention improves with transparency

What it is. An analysis of making context compaction explicit and inspectable in long coding-agent sessions.

Why it matters. Compaction is a hidden state transition; operators need to know what was dropped and what was retained.

Buildn/client use. Expose compaction events in Buildn logs with retained goals, decisions, files, and unresolved risks.

Why now. Long agent runs are becoming normal in coding and research workflows.

Caveat: Results may be sensitive to the task distribution and compaction implementation.
  • Next: Add a “context checkpoint” artifact to one long-running workflow.

History-Aware Compaction

ROUTINGPAPER
  • Source: arXiv 2610.08722
  • Signal: compaction should follow task state

What it is. A method for predicting when compaction will hurt by reading the agent’s history instead of applying a global token threshold.

Why it matters. A fixed threshold is cheap but blind; task-aware routing can preserve critical state while controlling spend.

Buildn/client use. Route compacting by phase: exploration, implementation, review, and handoff each preserve different evidence.

Why now. The same token budget cannot serve a debugging loop and a final handoff equally well.

Caveat: Needs calibration against real traces before becoming a default.
  • Next: Define phase-specific retention rules and test them on five traces.

SHarP Harness Pruning

LEANERPAPER
  • Source: arXiv 2610.04178
  • Signal: saliency-based tool reduction

What it is. A saliency-based approach to pruning agent harness components while retaining task-relevant tools and instructions.

Why it matters. Every tool and instruction is a liability surface and context tax; smaller harnesses can be safer and more reliable.

Buildn/client use. Create minimal client-specific harness profiles instead of giving every agent the full tool catalog.

Why now. Tool-rich systems are accumulating integrations faster than teams can evaluate them.

Caveat: Pruning can remove a low-frequency tool that matters in an edge case.
  • Next: Measure tool invocation frequency and delete the bottom 20% from a pilot.

EvoArena Memory Evolution

DYNAMICBENCHMARK
  • Source: arXiv 2606.13681
  • Signal: robustness under changing environments

What it is. A benchmark for whether agent memory evolves safely as tasks, tools, and environments change.

Why it matters. A memory that works on a static benchmark can become stale, brittle, or actively misleading after a system update.

Buildn/client use. Add environment-change tests to Buildn agent acceptance criteria.

Why now. Tool schemas, models, and workflows are changing weekly.

Caveat: Benchmark integration may require substantial setup.
  • Next: Create one “environment changed” regression test per critical workflow.

Agent Memory as a Runtime Budget

SYNTHESISPATTERN
  • Source: Editorial synthesis
  • Signal: latency, cost, retention tradeoff

What it is. A practical design pattern combining compaction, saliency, and query-time routing into one visible budget.

Why it matters. Teams can make better tradeoffs when retention, latency, and token spend are shown together.

Buildn/client use. Add a runtime scorecard: tokens retained, compaction count, recovery rate, latency, and cost.

Why now. Operational visibility is the missing layer between memory research and deployed agents.

Caveat: This is a synthesis, not a single source or validated benchmark.
  • Next: Instrument one workflow before optimizing its prompt or model.
