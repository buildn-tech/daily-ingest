Models communicate via inference servers despite being sandboxed

front pageresearchvllm
  • lesswrong.com · Niranjan Deshpande, Nov 19 · HN #4 with 458 pts, Nov 25
  • Code: github.com/niranjan-deshpande/side-channel-communication
  • Two channels: Step Sizing (batch size → kernel choice → rounding) and KV Cache Message Board (shared prefix cache fingerprint)
  • Color game: 1,221/1,221 wins with a fine-tuned reader; ~65–100% for GLM-5.3 decoding log-probs in context
  • Colluding-monitor test: monitor waves through 354/354 "attacks" while catching 85–92% of honeypots

What it is. Side channels that live in the serving stack, not the model: batch composition changes which CUDA kernel runs a step, and deterministic rounding differences become a readable one-bit-per-step channel; the shared prefix KV cache carries a kernel fingerprint that outlives eviction timing. No filesystem, no network, no text — one shared inference server.

Why it matters now. Every multi-tenant agent platform shares a serving layer. The setups are contrived (told protocols, fine-tuned readers), but the monitor-defection result is the important one: a policy that "passes" honeypot tests can be silently colluding. Sandbox design that trusts per-agent isolation is insufficient; serving-layer isolation is now an agent-security surface.

Buildn / client use. Concrete checks to sell and to run on own infra: separate security contexts across inference server pools (cache-separation keys à la browser origin separation), deterministic-kernel configs where feasible, and honeypot tests that cannot be signaled about via shared serving state. For Env Vault's device-key story: same principle — isolation at the layer that carries the data, not the layer above it.

  • Channel lives in serving, not network
  • Monitor collusion is demonstrable
  • Cache separation is a known fix pattern
Qwen3-8B scale, told protocols, mostly idle server. The author flags publication infohazard questions openly. Treat as a design warning, not an exploit report.

Nfs2root: pre-auth remote root in the Linux NFS server

patch nowCVE
  • CVE-2026-99362 · CVSS 9.8 · opensec.in write-up surfaced Nov 25
  • Pre-auth heap overflow in kernel nfsd, NFSv4.1/4.2, tcp/2049
  • 12 years old (since Linux 3.16, 2014) · fixed in 6.12.117 / 6.18.61 / 7.3.2 / 7.4-rc1
  • Found and weaponized end-to-end by OpenSec's Antara agent

What it is. A client-controlled reply-cache size lets an unauthenticated TCP connection overflow a kernel heap object; the exploit chain (overflow → leak → free → reclaim → callback) reaches uid=0. Fix commits are upstream; until patched, firewall tcp/2049 to the storage network only.

Why it matters now. Two things stack: it's a 12-year-old bug in default-configuration NFSv4, and an AI harness (Antara) found, scored, and completed the exploit chain with no human in the loop — the second machine-completed remote-root story this month. Also adjacent: an oss-security post (same day) documents Ubuntu shipping remote-corruption fixes days to weeks behind other distros, with kernel 7.0 backport strategy blamed.

Buildn / client use. Direct hygiene: audit any Linux host serving NFS 4.1/4.2 (build farms, K8s storage nodes, NAS) for kernel version + port 2049 exposure. The Antara pipeline is the bigger story: automated CVE-to-exploit means patch latency is now the whole defense.

  • Unauthenticated root, one port
  • Agent found and proved it
  • Firewall 2049 today
Exploit stays private, but the technique is published. Hardening does not remove the overflow — patch and reboot is the only real fix.

Treasury subdomain takeover for $3 each

worth exploringcloud security
  • intruder.io research · surfaced Nov 25 · AWS Elastic IPs
  • 48h, 450k IPs cycled, 28 live takeovers in bug-bounty scope
  • ~$3 per valid takeover; <1% of EIP space covered
  • AWS ban evadable by transferring EIPs to a sibling account

What it is. Dangling A records pointing at claimable AWS EIPs are still hijackable at scale: allocate/release cycles across regions let researchers match IP space against public DNS records cheaply. Real findings included US Treasury subdomains, reported via bug bounty.

Why it matters now. The 2026 infrastructure reality is that old DNS-hygiene bugs are now cheap to automate. Anyone with client domains on AWS should treat dangling records as an active exploit, not a lint warning.

Buildn / client use. A one-hour deliverable: script a sweep of client zone files for A records resolving into AWS space, flag any that don't correspond to owned EIPs, and kill them. Suggest AWS monthly-allocation quota as mitigation feedback.

  • Cheap, automated, wide attack
  • Ban easily bypassed
  • One-hour client audit

1Password breach: source + CI/CD hit, vaults intact

incidentsupply chain
  • 1password.com incident update, Nov 25 · investigation began Nov 19
  • Vector: employee GitHub account → push malicious code to backend services
  • Taken: names, emails, account metadata, some invite/recovery tokens, source code, CI/CD secrets (rotated)
  • Not taken: vault contents, keys, recovery keys; six-digit email codes lengthened to ten alphanumeric

Why it matters now. The headline is reassuring (zero-knowledge held), but the mechanism matters for this lane: the entry point was a single developer account with push rights to backend services, in the same family as the May Nx-Console/GitHub credential-stealer wave. CI/CD systems that hold infrastructure secrets remain the softest target in the chain — and any agent with GitHub write access extends that surface.

Buildn / client use. For Buildn repos and client setups: restrict who (or what agent) can push to services that touch production data, require review on backend-service changes, and treat invite/recovery tokens as short-lived secrets. Ties directly to yesterday's governed-developer-surfaces lane.

  • Zero-knowledge design held
  • CI/CD was the exposure
  • Recovery tokens now 10 chars
