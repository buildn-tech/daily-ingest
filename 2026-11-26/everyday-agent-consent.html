MCP grows: server Skills, long-running Tasks, Elicitation, File Uploads

strong signalprotocolanthropic
  • Anthropic MCP update · Nov 25, 2026
  • Skills: servers publish procedural knowledge (public beta)
  • Tasks: long-running async work, GA · Elicitation: pause-for-confirmation, GA
  • File Uploads: experimental, bypasses model context

What it is. The four extensions turn MCP from a tool-transport into an operational backbone: procedural knowledge lives on servers and stays current without re-prompting, work continues after background processing, approvals happen at defined pause points, and bulky files can move without consuming context.

Why it matters now. This maps almost one-to-one onto Buildn OS's design language: first-class tasks, explicit approval gates, and server-owned procedure (the skill-template HITL/AFK split). When the dominant agent protocol natively encodes the same primitives, Buildn's workflow model stops being a design position and becomes an integration target.

Buildn / client use. Prototype one MCP-backed skill for a repeatable client procedure (invoicing, research intake) to validate update and approval flows. Audit file-integrity and approval enforcement before touching File Uploads in production.

  • Procedure lives on servers
  • Resumable async tasks
  • Buildn model = protocol
Availability rolls by plan; File Uploads is explicitly experimental. Approval flows deserve the same audit treatment as payment flows.

Google Duplex returns: Gemini calls businesses for you

consumervoice
  • Google Tasks in Gemini · launched Nov 20, 2026
  • Agent calls businesses (bookings), self-discloses as AI
  • Businesses can opt out

What it is. Duplex's ideas at consumer scale inside Gemini: a personal agent that phones a business to make a reservation or appointment, with built-in AI disclosure and an opt-out path for the business on the other end.

Why it matters now. The disclosure-by-default design is the precedent to watch: consent is engineered into the call itself rather than handled by policy after the fact. Combined with the Dec 17 FCC blocking vote (voice lane today), everyday calling agents now have both a capability standard and a compliance deadline.

Buildn / client use. A pattern for any agent that acts on someone's behalf toward a third party: disclose at the boundary, offer the counterparty an exit, log everything. Worth mirroring in Buildn workflows that touch external systems.

  • Disclosure built in
  • Business opt-out respected
  • Consent as UX, not policy

MCP identity: first-class agent membership in orgs

worth exploringidentity
  • Enterprise platform updates tracked Nov 24–25, 2026 (Entra/Foundry-style blueprints)
  • Agents assigned a manager and a narrow permission scope
  • Audit on every agent action; separation of capability from access

What it is. Platform-level agent identities: an agent becomes an org member with its own owner, scope, and audit trail instead of borrowing a user's credentials. Capability (what the agent can do) separates from access (whose data it can touch).

Why it matters now. Yesterday's "whose agent is it?" lane ended on the boundary question; this is the structural answer arriving from enterprise platforms. The 1Password incident (security lane today) shows why credential-borrowing agents are a liability: one person's GitHub token becomes the whole backend's blast radius.

Buildn / client use. Buildn OS task design already assigns agents as participants; extend the same model to access: agent-specific scopes on repos, tools, and decrypt capability in Env Vault, with revocation that cascades like user offboarding.

  • Own identity, own scope
  • Audit every action
  • No borrowed credentials
