Persistent Agent Work + Permissioned Autonomy

Always-on agents are becoming project participants. The practical design question is how to make their context, permissions, and interruptions inspectable before “autonomous” becomes “unreviewable.”
Editorial readout: The strongest fresh product signal is not another chat surface: it is background work that persists, learns operating preferences, and pauses at consequential boundaries. This lane earns inclusion because it turns agent capability into an operating model Buildn can prototype.

Signal map

Recurring vocabulary: green edge = leverage; amber = caveat; red edge = risk or failure boundary.

OpenAI dots: a persistent worker model

signalpractical
  • source · OpenAI — Introducing dots
  • change · always-on cloud agents with browser/app access and Activity View

What it is

OpenAI describes dots as persistent agents with their own cloud computer and browser, access to 4,000+ apps, and cross-channel continuity through ChatGPT, Slack, and Teams.

Why it matters

This is a concrete reference model for work that continues after the prompt. Its value is the control surface: custom rules, read-only proactive research, auto-review, and visible activity.

Custom rules as an agent policy layer

signalpractical
  • source · OpenAI — dots safety and controls
  • change · explicit allow / require-approval / block rules around actions

What it is

Dots expose custom rules and action review to determine whether an action can proceed automatically, needs approval, or must stay user-controlled.

Why it matters

A reusable policy vocabulary is more valuable than a bespoke prompt. It separates user intent from the authority to act.

Buildn / client use

Turn Buildn tool permissions into named policies: read client source, draft artifact, request approval, publish artifact.
  • Policy before tools
  • Named escalation
  • Auditable decisions
Next: Write a four-level action policy for one Buildn tool family. · Caveat: Policy evaluation is only as strong as the action taxonomy and the system’s ability to enforce it.

Cross-channel continuity is a state problem

signalpractical
  • source · OpenAI — dots interaction model
  • change · projects continue across web, desktop, Slack, and Teams

What it is

The same dot can be reached through several surfaces while retaining relevant project context and permissions.

Why it matters

The interface is no longer the system boundary. State, identity, and approvals must travel with the work.

Buildn / client use

Model Buildn engagements as a durable run object with event history, current authority, artifact links, and a resumable handoff.
  • State follows work
  • Handoffs are explicit

Read-only proactive research as a safe default

signalpractical
  • source · OpenAI — dots proactive research
  • change · background research can use connected apps without mutating them

What it is

The described proactive mode gathers information and sends updates while disallowing messages, edits, or browser control.

Why it matters

Read-only is a useful first rung for agent adoption: it creates value without granting write authority.

Buildn / client use

Offer a weekly client signal scan that cites sources, flags changes, and asks before any CRM, CMS, or code mutation.
  • Low blast radius
  • Evidence first
  • Natural checkpoint
Next: Build a read-only source scan with citations and expiry dates. · Caveat: Read-only access can still expose sensitive data; data minimization remains mandatory.

Teams of agents need portfolio controls

What it is

OpenAI points toward users managing teams of dots across simultaneous projects and roles.

Why it matters

The scaling risk moves from “can one agent do this?” to orphaned work, duplicated authority, and unclear ownership.

Buildn / client use

  • Portfolio visibility
  • Easy shutdown
