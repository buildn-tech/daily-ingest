Chat SDK reactions and ephemeral messages on Teams

What changed
Vercel Chat SDK’s Teams adapter now supports reactions, targeted ephemeral messages, author emails, custom token factories, and better conversation routing.
Why it matters
Permission requests and private diagnostics no longer need to spill into a shared project channel; reactions can make long-running work legible.
Buildn / client use
Buildn: acknowledge intake with a reaction, send approval prompts privately, and publish only the final artifact to the shared thread. Client work: implement a consistent Teams agent interaction contract.
Caveat
An email identity supplied by a chat adapter is an input signal, not authorization proof; bind approval to your identity system.
Follow-up
Prototype one Teams intake flow: acknowledge → private approval → public completion.

Ephemeral Messages — Chat SDK

What changed
The SDK documents platform-specific persistence and required fallback behavior for private messages.
Why it matters
The same API has materially different records behavior across Teams, Slack, Google Chat, and Discord.
Buildn / client use
Buildn: define which approvals must become durable tickets. Client work: choose DM fallback deliberately, not as an accidental audit trail.
Caveat
Slack ephemeral messages disappear on reload; Discord generally falls back to a persistent DM outside interaction responses.
Follow-up
Write a retention decision beside each agent approval action.
release2026-07-30

Limit remote control to managed devices

What changed
GitHub added device-level remote-control eligibility through a managed `remoteControl` setting, including requireSSO, disabled, and enabled modes.
Why it matters
Remote control changes the risk profile of an agent session; device posture is a useful enforcement layer beyond an account policy.
Buildn / client use
Buildn: keep remote control disabled on shared runners. Client work: deploy requireSSO through MDM for approved operator workstations.
Caveat
This complements, rather than replaces, the enterprise-level remote-control policy.
Follow-up
Classify devices that may host remote control, then deploy the restrictive default.
